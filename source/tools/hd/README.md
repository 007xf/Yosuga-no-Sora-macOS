# 原素材保真高清处理

当前应用为1.2.1 / 20261024.1，增补明朝选项字体与普通消息点击保护；四倍素材文件及高清渲染保持1.2验收基线。最终证据为工作区 `outputs/32 功能补测/01 续作验证记录.md` 与第15、18、19号JSON。下文原1.2二进制及运行描述属于当次交付记录，不能用来识别当前安装。

这条流水线从两作现有素材的源像素制作四倍纹理，不调用生成模型，不重画人物、文字、构图，不添加黑色描边。原始 NOA、ERI、开场 MEI、脚本和存档均不由这条流水线改写。

## 覆盖范围与实际结果

2026-10-23 的原始清单有 4,888 个 ERI 素材条目；含 28 个各 27 帧的动画素材，共 5,616 个原始条目帧。当前启用的三个 mod 归档另有 90 个 PNG 条目；其余 ERI 已在原始清单内，避免重复计算。

按内容散列去重后，共有 3,497 个源文件、4,225 个独立画面帧。这些四倍 PNG 覆盖 4,978 个源条目及 5,706 个条目帧；所有帧均通过严格审查，未跳过任何失败素材。PNG 合计 10,952,667,947 字节，约 10.20 GiB。

原尺寸 800×600 的整屏画面输出为 3200×2400；1600×1200 的源画面输出为 6400×4800。所有单独的立绘、按钮及遮罩保持各自原比例，不能强行裁成 4:3。游戏视口的 4:3、Mac 显示器内的等比适配及真实高清纹理调用，已分别由最终运行报告与原生绑定回归验证，适用范围见后文。

本轮生成结果的最差数值仍在既有严格阈值内：

- Alpha 遮罩 IoU 最低 0.972803，要求至少 0.97。
- 缩回原尺寸后的平均色差最高 9.810540，要求不超过 10。
- 缩回原尺寸后的 SSIM 最低 0.940517，要求至少 0.90。
- 4,209 帧只使用 Alpha 正确的 Lanczos 插值；11 帧增加一次原像素一致性校正，5 帧增加两次。
- 实际接受的 4,225 帧均未使用半透明量化补偿。该保守后备分支只在单元测试中覆盖，不应描述成本轮素材的处理步骤。

## 像素与 Alpha 处理

ERI 的 `0x04000000` 表示带 Alpha，`0x08000000` 表示 RGB 未乘 Alpha。导出器保留原始 SDK 像素字节；未设置后一标记的带 Alpha ERI 因而仍是预乘 RGB，不能直接作为普通直通 Alpha PNG 解读，否则会出现重复乘 Alpha 的灰黑边。

`bulk_upscale.py` 先根据原 ERI 标记明确转换为正确的直通 RGBA 参考。转换前后原尺寸 Alpha 逐像素相等，不透明像素 RGB 逐像素相等。随后在浮点预乘 Alpha 空间做 Lanczos 插值，最后只反预乘一次，输出 8-bit RGBA PNG；完全透明像素 RGB 为零。带有效透明像素却标记 `opaque` 的输入会被拒绝。

若最初候选未通过严格阈值，程序只把“原像素减去候选缩回结果”的误差投影回来，最多三次，达到阈值立即停止。这是用原始观测约束插值，不包含外部图像先验、学习模型或凭空补充细节。半透明后备分支仅能触及原 Alpha 124–131 的舍入边界，单步不超过 8/255、总计不超过 16/255，而且仍须完整通过同一套严格审查。

比较参考是原图正确显示时的直通 Alpha 像素。既有 `check_hd.py` 及 `manifest.json` 均保持原样；不能把本轮明确的反预乘参考校正，描述成旧错误导出 PNG 的逐字节色值保持。插值也不能恢复源文件从未包含的真实细节。

## 构建、续跑与回读

项目根目录运行：

```sh
python3 -I tools/hd/bulk/inventory.py
python3 -I tools/hd/bulk/catalog_export.py --jobs 4
python3 -I tools/hd/build_bulk.py --workers 4 --scale 4
python3 -I tools/hd/verify_bulk.py hd/bulk --check-sources
python3 -I tools/hd/bulk/inventory.py --verify-sources
python3 -I tools/hd/test_bulk_upscale.py
```

1.2—1.3 的高清集还以 `--supplemental-catalog` 加入了旧「晴空」皮肤的 PNG（补充清单 03）；1.4 的皮肤纹理改由皮肤构建器以四倍原稿直接提供（见下文「打包存储」），不再需要这一步。

`hd/sources/<encoded_sha256>/frame0000.png` 是只读使用的解码源缓存；`metadata.json` 保留原尺寸、帧数、帧序、时长、格式和原点，并记录每个解码 PNG 的散列。`hd/bulk/<encoded_sha256>/frame0000.png` 是对应的四倍替换纹理。

每个输出先写临时文件，重新打开核对尺寸、RGBA8 格式和完整像素相等，再原子替换。单张审查记录在 `hd/bulk/audit/`；`02 处理进度.json` 是原子更新的进度，`03 处理日志.jsonl` 保留各次运行历史。续跑会同时核对处理版本、源 PNG 散列、倍率、Alpha 模式及输出散列。

`hd/bulk/manifest.tsv` 只有所有预期独立帧均通过时才发布。失败运行只产生 `manifest.candidate.tsv` 和完整失败记录，不把缺失画面的清单发布为完成。每行依次是：

```text
source_sha256<TAB>frame_index<TAB>logical_width<TAB>logical_height<TAB>relative_png
```

第一列必须是 NOA 成员解压后、原图解码前的文件字节散列，即清单里的 `source_sha256`，不能误用压缩存储载荷的 `encoded_sha256`，也不能使用解码 PNG 的散列。帧号从零开始，逻辑宽高保持原尺寸。原归档和 CPU 使用的遮罩、原始 Alpha 及动画语义仍由原文件提供。

本轮独立回读已验证全部 4,225 个替换 PNG 的文件散列、RGBA8 与精确四倍尺寸、原清单的逐帧覆盖和所有解码源 PNG 的不变性。另一次源文件回读确认 43/43 个原文件与初始清单散列一致，七项单元测试通过。三个当前 mod 归档也在提取前后逐个散列一致。

## 静态纹理与开场影片的验证边界

这条批处理包含普通 ERI 以及 ERI 素材内部的全部动画帧。原始两段 `opening.mei` 则是另外的有声视频流：缘之空 2521 帧、800×600、126000 ms；悠之空 3841 帧、800×600、127999 ms。它们进入原文件散列核对，但没有被 `build_bulk.py` 转成上述四倍替换 PNG。

因此“4,225 帧全部通过”只证明本清单中的静态/ERI 动画纹理制作及回读完整，不能单独证明两段开场影片已逐帧高清化，也不能代替真实游戏的纹理命中、播放帧序、音画同步、4:3 视口、Mac 分辨率和最终打包版运行验证。若影片走运行时缩放路径，必须另外记录该路径的实际生效证据；单纯放大显示不等于新增可恢复的源细节。

两段影片另在开发版完整播放至自然结束、返回标题，实际日志记录 `cubic=true uniform=present` 与当前解码纹理。播放验证早于最终 CPU 合成修复，之后影片 shader 和原视频字节未变；最终安装版没有重新完整播放两部影片，不外推静态 PNG 的逐帧 strict 指标。

## 原生运行层与安装核验

引擎用解码前的完整源文件 SHA-256 和帧号查找四倍伴随纹理。脚本、鼠标坐标、CPU 图像、遮罩、热点与动画时序保持原来的逻辑尺寸；绘制时才选择四倍纹理。根存储的关联随格式正规化、纹理对齐、裁片引用及完整裁切复制迁移，避免 800×1200 图集裁成 800×600 后失去来源。

普通二维父精灵和界面使用 CPU 缓冲。引擎保留原始 CPU 绘制，按同一次绘制遍历维护四倍合成结果，并在原缓冲完成写入后关联到父图。只有真正使用了高清来源或保留已有高清内容的会话才发布结果；纯 CPU 字形与灰度蒙版保持原始表示，避免将字体覆盖率误当作 RGBA 图片。高分辨率临时图带物理图标记，避免重复建立十六倍缓冲。当前不支持精确重建的细线、预设渐变、深度缓冲及自引用写入保留原绘制，使用当前纹理采样，不发布陈旧的伴随结果。

父级四倍合成图在连续局部刷新时，用 `CloneCPUCanvas` 对裁片做原预乘 Alpha 字节的深拷贝。已保留的像素不再经过“预乘→直通→预乘”的往返转换，避免每次光标刷新都累积整数舍入损失，造成文字中部变暗、空心或多重边缘。需要直通像素进行滤镜运算的 `CloneHDImage` 仍是另外的明确转换路径。首次从普通 CPU 图建立四倍底图时，整数双线性权重精确合计为 64，最后只舍入一次，保持恒定 255 Alpha 不被截断为 254。

六个真实素材、32 帧的原生绑定回归包括：完整源散列、原始 CPU 像素/尺寸/热点、动画首末帧、Alpha 只预乘一次、padded root→正规化→裁片、800×1200 背景上下半幅→800×600 父图→3200×2400 物理合成、局部刷新、全局仿射及透明度 0/128、纯 CPU 字形白色填充、混合高清背景与字形、写入失效和未知来源回退：

```sh
python3 -I tools/hd/bulk/test_runtime.py
```

`package_app.sh` 是打包入口：缺少高清存储或覆盖包时立即失败；安装存储后签名，再调用只读的 `verify_app.py`，不再改写包内容。`verify_app.py` 也可单独核验 stage 或安装目录：高清清单与文件散列（默认解码全部像素，`--no-decode` 跳过）、覆盖包与当前构建一致且每张贴图都有高清伴随、原始运行文件散列、版本、严格签名、无个人存档；拒绝逃出包内目录的路径或符号链接。

```sh
python3 -I tools/hd/verify_app.py '/Applications/缘之空.app' --report '/绝对路径/安装版核验.json'
```

正式运行核验须清除开发用 `ENTISGLS_HD_ROOT`，确认日志读取的是包内 `Contents/Resources/hd`。未设置该覆盖时，引擎按可执行文件的相对位置查找 app 自带的高清资源，不依赖项目目录。原游戏目录与个人存档不进入处理或测试写入路径。各版本的实测结果见 `HANDOFF.md` 与 Git 记录。

## 打包存储（1.4 起）

应用不再直接克隆上述 PNG。`tools/hd/pack_store.py build` 把两类经过审查的四倍纹理编码为无损 WebP，存入 `hd/store/`（增量、可续跑）：

1. 上文验收通过的原作纹理（`04 高清处理汇总.json`），去掉补充清单 03 中旧「晴空」皮肤的 PNG——新皮肤已不再引用它们；
2. 「空澄」皮肤每张纹理自己的四倍原稿（`mods/build/work/*/*/validation.json`），编码前核对原稿恰好缩回归档里的那张 PNG。

每个文件都在编码后解码比对：RGBA 像素与源 PNG 完全相同；同一画面只存一份。`pack_store.py install` 为应用写 `manifest.tsv` 并复制所需文件，`verify` 逐行核对清单、文件散列与（可选）解码像素。引擎在 `image_codec.cpp` 中以静态链接的 libwebp 解码，得到与 PNG 路径相同的直通 RGBA。1.4.0 的实测体积见 `HANDOFF.md`。
